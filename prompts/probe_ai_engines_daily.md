## ⛔ 红线（逐字保留，任何情况下不得改写、不得放宽）

- **浏览器自动化只读：零私信、零评论、零点赞、零连接请求。**
  本 playbook 会在两个 AI 引擎里**输入问题**——这是读取动作的必要输入，是被允许的；
  除此之外不做任何会留下公开痕迹的操作（不分享对话、不点赞回答、不提交反馈）。
- **频率写死**：探测日一次；**不得加频**。同一个问题一天只问一遍。
- **遇验证码或风控提示：立即停止、Telegram 上报、不重试；当周剩余扫描作废。**
- 写入只进**探测记录库**。本 playbook **不写水箱、不写 Query 库**。

**不要为了「让 Vivu 被引用」而调整问法。** 探测是量体温，不是治病。
把问题改成能引出品牌名的形式，等于把温度计放进热水里——数据当场作废，
而这份数据是 AEO 内容排期的唯一依据。

## 3. 逐步操作清单

对**每个引擎**（`probe.engines` 里的都要跑，顺序不限），对**每套问题的每一条**：

1. 打开该引擎的入口 URL。
2. **开一个新对话**再提问。
   > 这一条不能省：同一个对话里连问 10 条，后面的回答会被前面的上下文带偏
   > （尤其问过一次品牌名之后，后续回答出现该品牌的概率会假性升高）。
   > 每条问题一个干净对话，是这份数据能不能横向比较的前提。
3. **逐字粘贴问题原文**。不改写、不加限定词、不加「请列出工具名」这类引导。
4. **确认已提交——只看对话流，不看按钮。**
   判据是「**自己那条 user 消息已经出现在对话里**」。
   > Gemini 的发送键与 `Stop response` **共用同一个方形按钮位**：生成中它就是停止键。
   > 页面渲染有延迟时，按钮形状本身就是那个正在延迟的东西，
   > 拿它判断「提交了没有」永远判不准。2026-08-10 就是这么点停了三次生成。
   没看到自己那条 user 消息 → **等 15 秒重读一次页面**，仍没有才重新粘贴提交。
5. **提交之后到回答生成完毕之间，不点击输入框区域的任何按钮。**
   只等待、只滚动、只读取。这一条没有例外，包括「看起来像是没发出去」的时候。
6. 等回答完整生成（Gemini 会分段流式输出，等停）。
7. 按 §4 判定，按 §5 写探测记录库。
8. 不要点赞/踩、不要分享对话。
   **探测过程中不追问**——追问只在 §11 规定的那一个时机、用 §11 那句固定措辞，
   且必须在本条问题的探测记录已经写完之后。除此之外一律不追问。

### 中断与卡死怎么处置（2026-08-10 新增）

一次提问没拿到完整回答，可能是三件性质完全不同的事。**先分清是哪一件再动手**——
把它们混成同一个「没拿到」，等于把一次引擎信号写成自己的锅，或者反过来。

| 现象 | 是什么 | 怎么办 | 记什么 |
|---|---|---|---|
| 页面留 `You stopped this response` | **操作中断**：我们自己点停的，引擎没产出回答 | 探测问题 → 开新对话重问一次；追问 → 在原对话里重发一次那句固定措辞（逐字） | 上报里点名「操作中断，已重问」；追问位收 0 时 `zero_reason = 操作中断` |
| 提交后 **≥3 分钟零输出**、一直停在 `Stop response` | **零输出卡死**：不是操作错误，没人点它。疑似静默限流 | 刷新一次页面读同一对话。仍零输出 → 见下一行，**不换措辞重问** | `zero_reason = 零输出卡死` |
| 刷新后仍零输出（探测问题位），或当天累计 ≥2 次零输出卡死 | 该引擎当前不产出内容 | **走 §10 停机上报** | 同 §10 |
| 回答生成了，但答非所问 / 整段是解释性文字 | **内容不可用**：引擎答了，答得没用 | 现行 §11：收 0、**不重问、不换措辞** | `zero_reason = 引擎答非所问` |

**「操作中断可以重问一次」不是新开的口子。** §10 已经写着「回答明显被截断且重试一次仍截断」——
即已经承认「一次没拿到完整回答的提问可以重试一次」这条对频率红线的豁免。
我们自己点停与被截断在效果上是同一件事（都是一次没产出回答的提问），适用同一条豁免。
**豁免只有一次**：重问后再出问题，按上表往下走，不许第三次。

> ⚠️ **零输出卡死不要写成「操作错误」。** 没人点它的那一次，是引擎侧或会话侧的事。
> 把它归进自己的锅，就等于把一个可能的限流信号从上报里抹掉了——
> 这与 §10「把一次已知的数据污染变成一次无人知晓的数据污染」是同一个错误。

## 4. 判定规则（规则来自 config，本节只说怎么用）

### ① Vivu 是否被引用

读 `scan.yaml: probe.citation_rule` —— **回答正文出现品牌名即记引用**（逐字）。

- 匹配串取 `probe.brand_names`，大小写不敏感。
- **只看回答正文。** 侧边引用来源列表、脚注链接、Sources 类卡片里出现
  **不算**——spec 写的是「回答正文」。
- 命中 → 勾选 `Vivu 是否被引用`；未命中 → 不勾选。
- 不做「差不多算」的判断：没出现就是没出现。这个字段的价值全在它诚实。

### ② 品类答案是否形成

读 `scan.yaml: probe.category_answer_rule` 的三档分界（该节【推演待校准】，
Phase 0 只冻结了选项名没给定义）：

| 取值 | 分界 |
|---|---|
| `已形成` | 回答直接给出一类工具的名单并给出选型建议 |
| `雏形` | 回答绕着说、给的是通用做法或零散工具，没有成型的品类名单 |
| `无` | 回答答非所问，或明确表示不知道这类工具 |

三档的判定是本 playbook 最主观的一步。**判不准就往低了判**（雏形而不是已形成），
并把原句摘进 `回答摘录` 供真人复核。首轮盯跑时真人要专门抽查这一列。

### ③ 被引用竞品

把回答正文里出现的**产品名/公司名**逐个列出，逗号分隔。

- 只列**工具/产品**，不列通用做法（`use folder naming conventions` 不是竞品）。
- 不做判断、不做归类、不筛选「算不算真竞品」——照抄出现的名字。
- `scan.yaml: probe.known_competitors` 里的名字（当前 TwelveLabs / Twelve Labs / ChatCut）
  照常记进本字段，**另外**在上报里单独点出（见 §9）。
  它们是已知会被拿来比的对象，频次变化比陌生名字更值得看。
  **不在这张表里的名字一样要记**——这张表是「重点看」，不是「只看」。
  竞替名单的收敛是真人的活（`gates.yaml: competitor_list_converged` 当前 `false`，
  且明文「禁止脚本自动翻转：收敛与否是判断，不是计算」）。

## 5. 字段映射表（探测记录库 · 字段名逐字取自 Phase 0 核对清单）

| Notion 字段 | 类型 | 本 playbook 写什么 |
|---|---|---|
| `探测标识` | title | `YYYY-MM-DD` + 空格 + 引擎名（Phase 0 格式：日期空格引擎） |
| `日期` | date | 今天 |
| `引擎` | select | `ChatGPT` / `Gemini`（schema 里还有 `Perplexity` 选项，2026-08-07 起不再写入） |
| `问题集` | select | `任务式 pain feeler` / `评估式 decision maker` |
| `具体问题` | text | 问题原文，逐字，与 Query 库里的 `query 文本` 一致 |
| `品类答案是否形成` | select | `已形成` / `雏形` / `无`，按 §4② |
| `Vivu 是否被引用` | checkbox | 按 §4① |
| `被引用竞品` | text | 逗号分隔，按 §4③；无则留空 |
| `回答摘录` | text | `【模型：X】` + 关键段落摘录。**照抄原文**，不概括、不翻译 |

`回答摘录` 的 `【模型：X】` 前缀：X 写**该引擎当前实际显示的模型名**（§0 第 5 条抄下来的那个），
不是 `scan.yaml` 里的配置值。格式与 Reddit playbook 的 `【帖型：X】` 一致，都是借字段用、不改 schema。

> 为什么每条都要记：探测记录库的 9 个字段里没有「模型」这一列（Phase 0 冻结）。
> 不记的话，两周后回看数据时无法判断某天的异常是「引擎答案真的变了」还是「模型被切过」——
> 这两件事对 AEO 排期的含义完全相反。

> ⚠️ **`探测标识` 会大量重名**：格式是「日期空格引擎」，而一天里同一个引擎要写 10 条记录，
> 于是当天同一引擎的 10 行标题完全相同。
> 这是 Phase 0 冻结的格式，**不改 schema 是硬约束，所以照 Phase 0 写**，
> 靠 `具体问题` 区分。这一条已列入待拍板清单（见 README「遗留问题」）——
> 要不要把标识改成「日期 引擎 问题序号」需要解冻 Phase 0 字段表，不是本 playbook 能定的。

## 6. 去重规则

本 playbook 的去重口径与三份扫描 playbook 不同（写的是探测记录库，不是水箱）：

- 去重键 = `日期` + `引擎` + `具体问题`。
- 写入前查探测记录库：今天、这个引擎、这条问题**已有记录 → 跳过，不重复问**。
  （这既是去重，也是「一天只问一遍」这条频率红线的执行方式。）
- 跳过的计入 `skipped_dupe`。
- 补跑场景：当天前半程跑完 ChatGPT 就断了，修好后重跑本 playbook —— 
  已写的会被跳过，只补没写的。**这是允许的**，因为它不增加对引擎的提问次数。

## 7. 每轮上限

`caps.per_segment_per_round`（每 segment 10 条）**不适用于本 playbook**：
探测记录不按 segment 组织，写的也不是水箱。

本 playbook 的量上限由问题数决定：`questions_per_set × len(question_sets) × len(engines)`，
当前 `5 × 2 × 2 = 20` 条/天。**超过这个数就是哪里错了**（多半是没去重或重复跑），
停下来查，不要继续写。

## 8. 扫描日志

写 `logs/scan_YYYY-MM-DD.json`。本 playbook 没有 segment 维度，
`segment` 字段固定写 `未分类`——这样它既满足 spec §四 的记录结构，
又不会污染 Phase 1 按 A–E 算的信号命中率分母（`未分类` 不在 A–E 里）。

```json
{"date": "YYYY-MM-DD", "playbook": "probe_ai_engines_daily",
 "segment": "未分类", "hits": 20, "inboxed": 20, "skipped_dupe": 0}
```

- `hits` = 实际问出去并拿到回答的条数
- `inboxed` = 写进探测记录库的条数
- `skipped_dupe` = 因当天已有记录而跳过的条数

落盘：

```bash
echo '{"date":"…","playbook":"probe_ai_engines_daily","records":[…]}' \
  | python3 scripts/scan_log_append.py
```

**0 条也要写日志。**「探测连续 7 天有记录」是 spec §三 的验收项，也是调度试验的成功判据，
静默无法与漏跑区分。

## 9. 上报

发到绑定的 Telegram group（群 ID 见 `.env` 的 `TELEGRAM_GROUP_ID`）。**每天固定发一条**：

1. 日期，以及 `20 条预期 / 实际写入 N 条`
2. 两个引擎各自的完成情况（哪个没跑完、为什么）
3. **今日 `Vivu 是否被引用` 命中数**（当前预期是 0；哪天不是 0 是大事）
4. 今日出现频次最高的三个 `被引用竞品`
5. `scan.yaml: probe.known_competitors` 里的名字今天各被引用了几次（**单独一行**，
   即使是 0 次也要写 0——0 次本身是信息：引擎没把它们归进这个品类）
6. `品类答案是否形成` 的三档分布
7. 扫描日志是否已落盘；未落盘则附 JSON

Query 库无探测问题时（见 §2），上报内容改为一句「Query 库无探测问题，等待真人入库，今日未探测」。

## 10. 停机条件与上报（红线）

读 `scan.yaml: halt`。

**触发条件**：验证码 / 风控提示 / 被要求重新登录或二次验证 / 页面结构与本文描述不符。
本 playbook 还要加三条：
- 任一引擎提示**额度用尽 / rate limit / 请稍后再试**
- 任一引擎的回答明显被截断且重试一次仍截断
- **任一引擎当前模型与 `scan.yaml: probe.engine_models` 不一致**（§0 第 5 条）
- **零输出卡死**（2026-08-10 新增）：探测问题位提交后 ≥3 分钟零输出、刷新后仍零输出；
  或当天累计 ≥2 次零输出卡死（含追问位）。见 §3「中断与卡死怎么处置」那张表。
  > 为什么它是停机级：额度用尽会明说，静默限流不会。一个提交了、进了生成态、
  > 却永远不出字的对话，行为上与「被截断且重试仍截断」等价——
  > 区别只是它连第一个字都没给。按后者同级处理，不给它一个「再等等看」的口子。
  > 【推演待校准】3 分钟与 2 次这两个阈值出自 2026-08-10 那次实测（卡了 4 分钟以上），
  > 无更多样本支撑，攒够几次后由真人调。

> 模型不一致为什么是停机级、而不是「改回去接着跑」：
> 你**不知道它是什么时候被切的**。如果今天前半程已经用错模型问过几条，
> 那几条与之前 N 天的数据不可比，混进同一个基线里会污染整段趋势。
> 正确做法是停下、上报、让真人确认从哪天起被切过，再决定作废哪几天。
> 自行改回模型继续跑，等于把一次已知的数据污染变成一次无人知晓的数据污染。

**动作**
1. **立即停止本次探测，不重试。**（额度类问题尤其不要换账号、不要开无痕窗口绕开。）
2. **向 Telegram group 上报**：触发了哪条、停在哪个引擎的第几条问题、已写入多少条。
3. **当周剩余扫描作废**——含本周剩余的日探测、日小扫与还没跑的两个周扫。不补跑、不追量。

## 11. 追问：收 AI 建议的 query（Shawn 2026-08-05 指定新增）

### 为什么加这一步

Query 库现在是个封闭集合：里面的问题全是我们自己写在 `scan.yaml` 里的。
拿它推断「市场在问什么」，得到的是我们自己假设的回声。
追问是想借引擎手里的提问分布，拿回一批**我们没想到的问法**。

**但它是假设源，不是证据源。** 模型说人们常这么问，不等于有人真的这么搜过。
真正的证据是 Keyword Planner 回来的月搜索量。所以这一步的产出叫**候选**，
写进 Query 库时 `数据来源 = AI 建议`、`月搜索量` 留空——
排 AEO 内容优先级的人必须能一眼看出哪些词还没有任何市场证据。

### 什么时候问

每个引擎、每个问题集，**在该问题集最后一条探测问题的记录写完之后**，
在**那同一个对话里**追问一次。当前 = 2 引擎 × 2 问题集 = **4 次/天**。

> 为什么必须在记录写完之后：§3.2 那条——同一对话里的上下文会带偏后续回答。
> 追问放在最后，被污染的只有追问自身（它的产出本来就只是待验证假设），
> 探测记录不受影响。**追问之后该对话即结束，不得再问第二条探测问题。**

> 为什么不是每条问题都追问：那是 20 次/天。追问的回答质量不随次数线性增长，
> 噪音和写库量会。

### 问什么（逐字，不即兴改写）

措辞存在 `config/query_candidates.yaml` 的 `followup.text`，**以那里为准**，
本节这份是抄件，两边不一致时以 config 为准：

> What other questions do people commonly ask you that are related to the one
> I just asked? List only the exact phrasings people use, one per line,
> with no numbering, no explanation, and no commentary.

措辞刻意**不提任何品类词**（不说 video search、不说 asset management）：
话题由刚问过的那条探测问题自己带出来。我们每多塞一个词，
拿回来的就多一分是我们自己的假设、少一分是它观察到的提问分布。

**不得为了拿到更"相关"的结果而给它加限定词。** 这与 §红线 那句
「不要为了让 Vivu 被引用而调整问法」是同一条纪律：调了问法，拿回来的就是我们想听的话。

### 收什么

- **逐字照抄它给的每一行**，不改写、不翻译、不合并、不排序、不筛「哪条像好 query」。
  筛选是脚本按 `config/query_candidates.yaml` 的规则做的，不是你在这里做的。
- 每次最多收 `caps.max_per_ask`（当前 5）条。它给 30 条时，后面那些是它在凑数。
- 它答非所问、或整段都是解释性文字 → 这一次收 0 条，如实记 0，不重问、不换措辞。
- **收 0 必须带原因，且必须落盘**（2026-08-10 新增，见下）。

### 产出落到哪

**不写探测记录库、不写水箱、不写 Query 库**——§红线 的三条禁令一条未破。
追问的产出只落一个本机文件（不是库）：

```bash
echo '{"date":"YYYY-MM-DD","engine":"ChatGPT","question_set":"任务式 pain feeler",
       "asked_after":"<刚问完的那条探测问题原文，逐字>",
       "suggestions":["<逐字第一行>","<逐字第二行>"]}' \
  | python3 scripts/query_candidates.py --stage
```

`--stage` = 进候选池，**不写 Notion**。写 Query 库是另一条命令（`--commit`），
由真人在看过当天候选之后执行——这一步刻意不自动化。

**收 0 的那一次也要跑这条命令**（2026-08-10 新增）：`suggestions` 给空数组，
另给 `zero_reason`，取值逐字取自 `config/query_candidates.yaml: zero_reasons`
（当前三个：`引擎答非所问` / `操作中断` / `零输出卡死`，判定按 §3 那张表）：

```bash
echo '{"date":"YYYY-MM-DD","engine":"Gemini","question_set":"评估式 decision maker",
       "asked_after":"<刚问完的那条探测问题原文，逐字>",
       "suggestions":[],"zero_reason":"零输出卡死"}' \
  | python3 scripts/query_candidates.py --stage
```

零收记录落 `data/query_candidates_zero.jsonl`，**不进候选池**（池子里只放候选本身）。

> 为什么非要落这一行：2026-08-10 之前，收 0 在数据里**不留任何痕迹**——
> 脚本只对非空 suggestions 追加行，候选池里没有「Gemini 今天两次都没收着」这回事，
> 唯一的记录是 Telegram 上报那一句。两周后回看，
> 「Gemini 追问零产出」会被读成引擎特性，而当天真实的原因是我们自己点停了它。
> 三种 0 的含义完全不同：`引擎答非所问` 是引擎信号，另外两个是我们这边的事故。
> 混算一个 0，这条链的产出率就是一个没法解释的数。

落不了盘时（会话无本机文件系统权限，Phase 2 §八④ 已知情形）：
把上面那段 JSON **原样贴进当天上报**，由真人管道喂进去。**不要因为落不了盘就跳过追问。**

### 上限与计数

- 追问次数上限 4 次/天，与 §7 的 20 条探测问题上限**分开计**。
  超过 4 次就是哪里错了（多半是每条问题都追问了），停下来查。
- **这个 4 次按「追问轮次」计，不按发送次数计**（2026-08-10 明确）：
  §3 那张表允许操作中断后重发一次同一句措辞，那一次是同一轮的补完，不新增一轮。
- 追问**不计入** §8 扫描日志的 `hits` / `inboxed`——那两个字段是探测记录库的口径，
  追问不写那个库。扫描日志一个字段不增不减。
- 当天追问了几次、各收了几条，写进 §9 上报（见下）。

### 上报里加两行

§9 那七条之后追加：

8. 追问 `N/4` 次，共收 M 条建议（**0 也要写 0**）；
   若有收 0 的，**逐次写明 `zero_reason`**（`引擎答非所问` / `操作中断` / `零输出卡死`），
   不许只报一个总数——三种 0 的含义不同，合并上报等于没报。
9. 若落盘失败：贴出那几段 JSON 原文
10. **当天发生过操作中断 / 零输出卡死的，逐次写明：哪个引擎、第几条问题、
    是探测位还是追问位、有没有重问、重问后拿到没有。** 一次都没有就写「无」。
